## 2025-02-14 - Fix Server-Side Request Forgery (SSRF) and Information Leakage in API Routes
**Vulnerability:** The `/api/enrich` route accepted arbitrary URLs and followed redirects (`redirect: "manual"`) without any protocol or domain validation, allowing potential Server-Side Request Forgery (SSRF) where an attacker could provide a URL that resolves to internal network services or malicious domains. Additionally, API routes (`/api/enrich`, `/api/categorize`, `/api/recommend`) leaked internal error details (`String(e)`) in their 500 error responses.
**Learning:** Manual redirect following via `fetch` requires strict validation at every step of the redirect chain, not just the initial input URL. Naive substring matching (e.g., `.startsWith('google.')`) is insufficient for domain validation as it can be bypassed (e.g., `google.attacker.com`). Returning raw error objects in catch blocks exposes internal implementation details (e.g., stack traces or API responses) which should be sanitized before reaching the client.
**Prevention:** Implement strict protocol (`http:`/`https:`) and domain allowlisting (e.g., exact matches for `maps.app.goo.gl` and `.google.com` subdomains, or precise regexes) before every `fetch` call when manually following redirects. Ensure catch blocks return generic error messages (e.g., "An error occurred") for unexpected 500 errors.
