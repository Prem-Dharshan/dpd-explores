## 2024-05-17 - SSRF Vulnerability in URL Enrichment
**Vulnerability:** The `/api/enrich` endpoint expanded user-provided URLs in `maps.app.goo.gl` links without any protocol or hostname validation before calling `fetch()`. This could lead to a Server-Side Request Forgery (SSRF) vulnerability where an attacker could provide an arbitrary URL (e.g., pointing to internal network services like `http://169.254.169.254` or `file:///etc/passwd`) and the server would attempt to fetch it, following redirects blindly. Additionally, error messages exposed raw stringified error objects (`String(e)`) which could leak internal path or stack trace details on failures.
**Learning:** External URL resolution paths (especially those handling URL shorteners and redirects) are extremely dangerous and must be explicitly constrained. Naively passing user-controlled strings to `fetch()` without analyzing their schema or resolving the final destination leaves the server open to internal network probing. Furthermore, raw error messages returned to the user can aid attackers in reconnaissance.
**Prevention:** Always enforce strict schema (e.g., `http:`/`https:`) and explicit hostname allow-lists when fetching user-provided URLs. For Google Maps links, validate domains rigorously (e.g., `maps.app.goo.gl`, strict `.google.com` endings, and regional domains via specific regex). Additionally, implement robust `catch` block error handling to map specific known client errors to targeted `4xx` responses while obscuring sensitive details behind generic `500` error messages for internal exceptions.
